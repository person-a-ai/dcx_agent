## 1. 의도 — 사용자가 말한 것과 가정 구분

**사용자가 말한 것**
- 지금은 공개 카페·블로그 위주라 유의미하지 않은 원문이 너무 많다.
- 생활 맥락이 드러나는 원문을 늘리고 싶다. 유튜브는 댓글보다 생활을 담은 브이로그 영상 내용 위주로 보고 싶다.
- 채널 확장 대상: 유튜브 브이로그, Threads, 그리고 앞서 제안받은 지식iN 질문, 82쿡 (4개 확정, 2026-10-19 대화).
- 페이스북은 제외. LinkedIn은 검토 후 제외(로그인 벽 · robots 전면 차단 · 주제가 일·커리어에 치우침).

**사용자 결정 (브레인스토밍 질의, 2026-10-20)**

| # | 질문 | 결정 |
|---|---|---|
| Q1 | Threads 수집 경로 | 로그인 없는 검색 화면을 먼저 수집하고, 공식 API로 바꿔 끼울 수 있게 만든다 |
| Q2 | 브이로그 자막 문서 단위 | 화제 전환 지점에서 자른다 |

| Q4 | 브이로그 영상 선별 | 검색어에 "브이로그"를 붙이고 길이로 거른다 |

**가정 (확인 필요 시 설계 단계에서 다시 묻는다)**
- G1. 이 도구는 맥미니 로컬 내부 실험용이다(D-002). 외부 공개 서비스가 아니다.
- G2. 로그인 · 쿠키 · 캡차 우회 · 프록시 회전은 어떤 채널에서도 하지 않는다(D-094 원칙 유지).
- G3. 82쿡은 자유게시판(`bn=15`)만 대상으로 한다.

## 2. 문제 — 지금 무엇이 부족한가

- 현재 채널은 네이버 블로그 · 카페, 유튜브 댓글, 클리앙, 뽐뿌 5개다. 블로그는 체험단 · 홍보 글 비중이 높고, 유튜브는 댓글만 모아 영상 속 생활 장면을 놓친다.
- 채널별 잡음 비율은 아직 측정하지 못했다(운영 데이터가 맥미니에만 있음). 이번 확장 후 라벨링 관련 판정 비율로 채널을 비교한다.
- 확인한 사실 (2026-10-19~20 조사)
  - Threads: 로그인 없이 `threads.com/search` 결과가 렌더링된다. 내용은 생활 발화 밀도가 높다. 단, 18~21건 뒤 스크롤하면 로그인 창이 뜨고 더 나오지 않는다. 공식 API는 무료지만 `threads_keyword_search` 앱 심사가 필요하다(하루 2,200회).
  - 유튜브: `"에어컨 브이로그"` 검색 상위 6개 모두 한국어 자동 자막이 있었다. 단, 상위 5개가 12~68초 쇼츠였다 → 길이 거르기가 필수다.
  - 지식iN: robots.txt가 검색 · 질문 페이지를 허용한다. 일반 HTTP 요청으로 페이지당 질문 15건이 나온다.
  - 82쿡: robots.txt가 게시판 · 검색을 허용한다. 일반 HTTP 요청으로 자유게시판 검색 결과 글 29건 링크를 확인했다.

## 3. 범위

### 채널 정의

| 채널 ID (화면 이름) | 목록 (P1) | 상세 (P3) → 문서 | 기본 동시 수 / 요청 간격 |
|---|---|---|---|
| `youtube_vlog` (유튜브 브이로그) | yt-dlp `ytsearch`로 `"{키워드} 브이로그"` 검색. 60초 미만 · 60분 초과 제외 | 한국어 자막(수동 우선, 없으면 자동)을 화제 단위 구간으로 나눠 **구간마다 문서 1건**. 한국어 자막이 없으면 `skipped`(`no_ko_captions`) | 2 / 0초 |
| `threads` (Threads) | Crawl4AI로 로그인 없는 검색 화면 렌더링. 인기 · 최신 두 화면을 합쳐 중복 제거 | 목록 항목이 곧 문서(본문 = 글 전문). 상세 요청 없음 | 1 / 2초 |
| `naver_kin` (지식iN) | `kin.naver.com/search/list.naver` 페이지당 15건 | 질문 페이지의 제목 + 질문 본문. 답변 수는 `src_meta.answer_count` | 1 / 0.5초 |
| `cook82` (82쿡) | 자유게시판 검색 `enti.php?bn=15` | 글 본문 + 댓글 | 1 / 0.5초 |

### 새 부품
- `backend/app/crawl/adapters/youtube_vlog.py`, `threads.py`, `naver_kin.py`, `cook82.py` — 채널마다 파일 하나, 기존 `ChannelAdapter` 규약(`list_page` → `fetch`)을 따른다.
- `backend/app/crawl/captions.py` — 자막을 화제 단위로 자르는 순수 함수. 약 20초 창으로 나눠 임베딩하고, 이웃 창 유사도가 떨어지는 곳에서 자른다. 구간 길이 하한 · 상한(기본 45초 · 5분)은 설정값이다. 임베더(`app/vectors/embedder.Embedder`)를 인자로 받는다. 임베더가 미연결이거나 실패하면 고정 90초 구간으로 대체하고 `src_meta.segmenter`에 사용 방식을 남긴다.
- `backend/app/crawl/render.py` — Crawl4AI 브라우저 하나를 유지하고, 동기 워커 스레드에서 비동기 Crawl4AI를 호출하게 잇는 다리. Threads만 쓴다.
- Threads 어댑터 안의 "검색 공급자" 경계 — 이번에는 화면 공급자만 구현하고, 공식 API 공급자를 같은 자리에 끼울 수 있게 한다.

### 문서 식별
- 브이로그 구간은 `FetchedDoc.thread_key = "{시작초}-{끝초}"`로 doc_id를 가른다(`sha1(URL + thread_key)`). 같은 영상 · 같은 자막 · 같은 임베더면 항상 같은 구간 · 같은 doc_id가 나온다.
- doc_id 접두사를 `urls.py`에 추가한다: `yv`(브이로그), `th`(Threads), `kn`(지식iN), `c8`(82쿡).

### 같이 고칠 기존 파일
- 백엔드: `crawl/schema.py`(`Doc.source`), `context/models.py`(`Channel`), `crawl/urls.py`, `crawl/adapters/__init__.py`(등록), `crawl/worker.py` · `crawl/control.py`(채널 기본 한도), `context/labels.py`(채널 이름), `prep/boilerplate.v1.json`(채널별 상투어 목록), `keywords/prompts.py`(구어 허용 채널에 `threads` · `cook82` · `naver_kin` 추가), `crawl/report.py`(skipped 사유별 집계)
- 프론트: `components/crawl/Settings.tsx`(채널 표, 브이로그 설정: 키워드당 영상 수 · 길이 범위), `lib/logic/crawlConfig.ts`(채널 기본값), `lib/contextLabels.ts`, `components/prep/prep.ts`, 게이트 안내 문구(Threads 수집량 안내)

## 4. 대안

| 결정 | 고른 것 | 버린 것과 이유 |
|---|---|---|
| Threads 경로 | 로그인 없는 화면 + API 교체 경계 | 공식 API만: 앱 심사 통과 전까지 채널을 못 씀. 외부 대행(Apify): 결제 계정 필요, 약관 위험이 업체로 옮겨갈 뿐 |
| 화제 분할 | A. 임베딩 유사도 | B. LLM 경계: 호출마다 결과가 달라져 근거 인용 · 버전 비교가 흔들림, 비용 큼. C. 고정 구간 후 전처리 병합: 수집 · 최종 문서 ID가 달라져 인용 추적이 복잡 |
| 유튜브 구성 | 별도 채널 `youtube_vlog` | 기존 채널 교체: 기존 세션 · 모델의 `youtube` 의미가 바뀜. 한 채널에서 둘 다: 영상 선별 기준이 섞임 |
| 자막 없는 영상 | 건너뛰고 건수 기록 | 설명란 대체: 협찬 · 링크 문구가 많음. 화면 글자 OCR: 영상 프레임 수집이 필요해 "영상 자체는 받지 않는다" 원칙과 맥미니 부하에 어긋남 |
| 분류 모델 채널 특징 | 이번에 늘리지 않음(새 채널은 채널 특징 0) | 늘리기: 입력 차원 1032가 바뀌어 기존 학습 모델이 모두 깨짐 → 백로그 |

## 5. 수용 기준

- AC-01. 네 채널이 크롤링 설정 화면에 나오고, 사용 가능 여부가 실제 조건(실제 채널 스위치 `REAL_CHANNELS_ENABLED`, yt-dlp 설치, Crawl4AI 브라우저 설치)대로 표시된다.
- AC-02. 각 채널을 켜면 기존 흐름(목록 → 게이트 → 상세 → 보고서)으로 끝까지 돈다. 이어 하기 · 중지 · "여기까지로 마치기"가 기존 채널과 같게 동작한다.
- AC-03. 브이로그 목록은 60초 미만 · 60분 초과 영상을 포함하지 않는다(경계값은 설정으로 바꿀 수 있다).
- AC-04. 브이로그 문서는 화제 단위 구간으로 나뉜다. 구간 길이는 하한 · 상한을 지키고, 같은 입력은 같은 구간 · 같은 doc_id를 만든다.
- AC-05. 임베더가 미연결이거나 실패하면 고정 90초 구간으로 대체되고, 문서의 `src_meta.segmenter`에 대체 여부가 남는다.
- AC-06. 한국어 자막이 없는 영상은 문서를 만들지 않고 `skipped`(`no_ko_captions`)로 남으며, 보고서에 채널별 사유 건수로 집계된다.
- AC-07. Threads에서 로그인 창이나 빈 결과가 오면 로그인을 시도하지 않고 `AdapterBlocked`로 처리된다. 연속 차단 기준을 넘으면 채널만 멈추고 다른 채널은 계속 돈다.
- AC-08. 지식iN 문서는 제목 + 질문 본문만 담고 답변 본문은 담지 않는다. 답변 수는 `src_meta.answer_count`에 남는다.
- AC-09. 82쿡 문서는 자유게시판 글 본문 + 댓글을 담는다.
- AC-10. 새 채널 문서가 전처리 → 라벨링 → 학습까지 오류 없이 지나간다(분류 모델 입력 차원 1032 유지).
- AC-11. 어댑터 테스트는 녹화한 실제 응답으로 네트워크 없이 돈다. 기존 채널 테스트는 모두 그대로 통과한다.
- AC-12. 실제 사이트 수동 확인(채널별 키워드 2개)을 구현 보고서에 남긴다.

## 6. 제외 범위

- Threads 공식 API 공급자 구현(교체 경계만 만든다), Threads 답글 수집.
- 지식iN 답변 본문, 82쿡 자유게시판 외 게시판.
- 말 없는 영상의 화면 글자 인식(OCR) · 직접 음성 인식.
- 분류 모델 채널 특징 확장과 재학습.
- 수집 정책(robots.txt · 약관) 정리 문서 — 별도 작업.
- 사이드바 챗봇(B-120) — 별도 백로그.

## 7. 위험

| 위험 | 영향 | 대응 |
|---|---|---|
| Threads 화면 수집이 Meta 약관의 자동 수집 금지 조항과 충돌할 수 있음 | 차단 · 정책 문제 | 로그인 · 우회 없이 공개 화면만, 요청 간격 2초, 공식 API로 교체 가능한 경계. 수집 정책 문서에서 팀이 판단 |
| Threads 로그인 없는 결과가 키워드당 수십 건 | 게이트 `low` 배지가 자주 붙음 | 안내 문구로 알림. 채널 비교는 관련 판정 비율로 |
| 유튜브 자막 내려받기에 봇 확인 · 추가 토큰 요구 | 브이로그 수집 실패 | 기존 `AdapterBlocked` 처리, 설계 단계에서 yt-dlp 자막 경로를 실제로 확인 |
| 말 없는 감성 브이로그 비중이 높음 | 브이로그 수집량 감소 | `no_ko_captions` 건수로 측정 후 OCR 여부를 따로 결정 |
| Crawl4AI · Playwright Chromium 부하 | 맥미니 처리량 · 메모리 | 브라우저 1개 유지, Threads만 사용, 동시 수 1 |
| 지식iN · 82쿡 화면 구조 변경 | 파싱 실패 | 녹화 응답 테스트 + 파싱 오류로 드러냄(조용한 과소 수집 방지) |
| 새 채널이 분류 모델 채널 특징 0으로 들어감 | 채널 신호 손실 | 백로그로 특징 확장 · 재학습 검토 |
