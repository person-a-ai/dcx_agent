# GPT(Codex) 판정 묶음 실패 내성 — 기획

## 문제
- 4단계 GPT 판정에서 묶음(20건) **하나만 실패해도 판정 전체가 자동 일시정지**된다(`judge.run_worker` → `gpt.LabelerPaused` → `_pause`). 사람이 "이어서 진행"을 눌러야 다시 돈다.
- 운영 실측(세라젬, 2026-10-20 21:00~21:38): 묶음 약 250개 중 11개 실패 → 자동 정지 7회. 마지막 정지를 아무도 풀지 않았고, 22:28 배포 재시작으로 "중단" 상태가 되어 다음 날 12시까지 멈춤. 2026-10-21 v3(5,688건)에서도 시작 11분 만에 같은 정지 발생.

## 원인 (운영 로그 확인)
| 유형 | 건수 (10-20) | 내용 |
|---|---|---|
| A. 답 파일 이름 미변경 | 7 | 지시문 `답만 answers/task-0.json.part에 쓰고 rename하라`가 **바꿀 이름을 말하지 않는다**. Codex가 임시 파일을 `.part`로 옮기는(`mv /tmp/task-0.json.part answers/task-0.json.part`) 것을 "rename"으로 해석하고 끝냄. 답 내용은 `.part`에 정상으로 남아 있음. `_worker`는 `task-0.json`만 찾으므로 "백엔드 실패". |
| B. 모델 용량 초과 | 4 | `ERROR: Selected model is at capacity`. 모두 21:00 시작 직후 동시 20개를 띄운 순간에 몰림. 일시적 오류. |

- A·B 모두 `failure('backend')` → 사용량 한도가 아닌 `LabelerPaused` → 묶음 글 20건에 실패 1회 기록 + **전체 일시정지**.
- 글 단위 "3회 실패 시 제외"는 이미 있다(`VoteCache.fail`: `attempts+1>=3`이면 `bad`). 그러나 매 실패마다 전체가 멈추므로 사람이 누르지 않으면 3회까지 가지 못한다.

## 사용자 제안과 판단
- 제안: "문제가 생기는 원문은 3회 시도하고 안 되면 넘기자."
- 판단: **동의.** 글 단위 3회 → 제외 규칙은 이미 있으니 그대로 쓰고, 그 규칙이 동작하도록 "묶음 하나 실패 = 전체 정지"를 없앤다. 다만 두 가지를 같이 해야 한다.
  1. 원인 A·B를 고쳐 제외되는 글 자체를 거의 없앤다. 그대로 두면 정상 글이 지시문 해석 운에 따라 제외된다(10-20 기준 약 4%의 묶음).
  2. Codex 장애·로그아웃처럼 **모든 묶음이 실패하는 상황**에서는 계속 돌면 몇 분 만에 전체 글이 3회 실패로 제외된다. 연속 실패가 이어지면 지금처럼 일시정지하는 차단 장치를 둔다.

## 대안
| 안 | 설명 | 판단 |
|---|---|---|
| A. 그대로 | 실패마다 사람이 재개 | 거절 (밤새 멈춤) |
| B. 원인만 수정 | 지시문·용량 재시도만 고침. 다른 원인의 실패엔 여전히 전체 정지 | 부족 |
| C. 정지만 제거 | 실패 묶음은 3회 후 제외, 정지 없음 | 위험 (장애 시 전체 글 제외, 원인 A로 정상 글 제외) |
| **D. 원인 수정 + 정지 제거 + 연속 실패 차단 (추천)** | A·B 수정, 단발 실패는 건너뛰고 계속, 연속 실패만 정지 | 선택 제안 |

## 동작 (예시, 안 D)
- 묶음 1개가 답 파일 이름을 안 바꿈 → `.part`가 스키마 검증을 통과하면 그 답을 그대로 채택. 실패 아님.
- 묶음 1개가 "model at capacity" → 잠시 뒤 같은 묶음을 자동 재시도(최대 2회 추가). 그래도 실패면 그 20건에 실패 1회 기록 후 다른 묶음은 계속. 이 20건은 나중에 다시 임대되어 최대 3회까지 시도, 3회 실패 시 "판정 실패로 제외".
- 묶음 실패가 성공 없이 연속 N회(예: 5회) 이어짐 → 지금처럼 일시정지 + 사유 표시. 사용량 한도는 기존대로 즉시 일시정지.
- 판정 화면에 "판정 실패로 제외 N건"이 보인다.

## 수용 기준
- AC1: Codex 지시문이 최종 파일명(`answers/task-{n}.json`)을 명시한다.
- AC2: 최종 답 파일이 없고 `answers/task-{n}.json.part`가 스키마를 통과하면 그 답을 채택한다(통과 못 하면 기존 형식 오류 처리).
- AC3: "model at capacity" 등 일시적 용량 오류는 묶음 단위로 짧게 대기 후 자동 재시도한다(최대 2회 추가). 사용량 한도는 재시도하지 않는다.
- AC4: 사용량 한도가 아닌 묶음 실패는 판정 전체를 일시정지하지 않는다. 해당 글에 실패 1회를 기록하고 다른 묶음은 계속 진행한다.
- AC5: 글이 3회 실패하면 판정 실패로 제외(`bad`)되고, 판정 완료 조건에 막히지 않는다(기존 규칙 유지 확인).
- AC6: 성공 없이 연속 N회(설정, 기본 5) 묶음이 실패하면 기존처럼 일시정지하고 사유를 보여준다. 사용량 한도는 기존대로 즉시 일시정지.
- AC7: 판정 진행 카드에 판정 실패로 제외된 글 수가 보인다(0이면 숨김).
- AC8: 백엔드 pytest · 프런트 lint · build · test 통과.

## 제외 범위
- 배포 재시작 시 진행 중 판정을 자동으로 이어 가는 기능(별도 작업으로 제안).
- 제외된 글을 다시 판정하는 버튼, 묶음 크기·동시 수·모델·프로필 변경, Jev 경로, OpenAI API 경로 재시도 정책.
- 이미 운영 데이터에 기록된 실패 횟수 정리.

## 위험
- 연속 실패 기준 N이 너무 크면 장애 시 많은 글이 제외되고, 너무 작으면 다시 자주 멈춤 → 설정값으로 두고 기본 5(동시 20에서 약 묶음 한 차례 분량의 1/4).
- `.part` 채택 시 Codex가 쓰는 도중 파일을 읽을 위험 → 프로세스 종료 후에만 확인하므로 해당 없음. 스키마 검증으로 잘린 파일은 거부.
- 용량 재시도가 동시 20개에서 겹치면 다시 용량 초과 → 대기에 무작위 지연을 섞는다.
- 제외된 글은 학습·클러스터링 입력에서 빠진다 → 화면에 건수를 보여 사용자가 알 수 있게 한다.
