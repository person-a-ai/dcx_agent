## 반복 검증 및 최종 검토

수거 시 모든 완료 future를 성공/실패로 구분해 성공부터 처리한다. `future.exception()`은 이미 완료된 future에만 호출된다. 상태(evidence, failed_at, consecutive_failures)와 cache 변경은 메인 스레드 collect에서만 수행하므로 별도 락이 필요 없다. 스레드 소유권 검증은 기존 fixture를 유지했다.

pause/error 직전 drain도 동일 collect를 호출하므로 성공 우선·사용량 한도 우선순위·시도 횟수 보존이 적용된다. 이미 정지 조건이 성립해 paused를 세운 뒤 drain에서 성공이 도착해도 정지 결정을 취소하지 않는다. 사용량 한도는 breaker보다 우선한다. 일반 예외 전파와 missing 처리, openai_api/fake의 즉시 정지 정책은 유지한다.

`release_docs`는 self.run_id와 pending 조건을 함께 사용한다. 지정 목록에 다른 run의 글이나 terminal 글이 있어도 변경하지 않는다. attempts/status/last_error/at는 보존한다.

`test_chunk_failures_preserve_peers`는 초기 4묶음을 함께 수거하도록 wait를 고정했다. backend 변형에서 시작 attempts=0이면 다른 3묶음의 성공(evidence=3) 뒤 d000·d001의 첫 실패가 attempts=1/pending이 된다. 새로운 성공 없이 반복 실패해도 attempts=1이며, 5회 연속 실패로 BREAKER_MESSAGE 정지, run paused가 된다. 나머지 6건은 done이다. 시작 attempts=2이면 첫 유효 실패로 attempts=3/bad가 되어 전체 종료하며 pause하지 않는다. mixed는 사용량 한도가 우선하므로 사유 usage limit로 paused이다.

성공 없는 장애는 attempts=0뿐 아니라 기존 attempts=2도 보존한다(동일 테스트의 매개변수 변형). 사용자 재개는 evidence를 늘리므로 꼬리의 문제 글이 재개마다 최대 1회씩 추가로 실패해 결국 attempts=3/bad가 된다. paused_codex는 run 사이 evidence를 보존하지 않으므로 4번 실행해도 attempts=0/bad=0이다.

최종 검토에서 성공 우선 테스트에 실패 글 6건의 attempts=1 검증을 추가했다. 리팩터링 검토 후 label 전체를 연속 3회 실행했다. `git diff --check`도 통과했다.
