- 앞선 실행: `label-import`(네이버 카페 전용 가져오기, 2026-11-04 UAT 승인). 이번 실행은 그 기능을 넓힌다.

## 문제

- 롱제비티 프로젝트 데이터는 채널 4개의 zip으로 왔다. 모두 같은 크롤러 원본 10개 컬럼 + dcx-label 결과 컬럼(+`error`) 구성이고 `q1`/`r1`이다.

  | 파일 | CSV | 행 | done / skipped | site | doc_id |
  |---|---|---|---|---|---|
  | 네이버 카페.zip | jev_longevity_full.csv | 197,913 | 195,446 / 2,467 | `네이버카페` | `nc_` + DCX 규칙 |
  | 네이버 지식인.zip | jev_jisikin_full.csv | 155,136 | 151,133 / 4,003 | `네이버지식인` | `kn_` + DCX `naver_kin` 규칙과 일치 |
  | 다음 브런치.zip | jev_longevity_brunch_full.csv | 171,505 | 171,497 / 8 | `다음블로그_브런치` | `db_` + sha1(URL)[:16] |
  | 다음 카페.zip | jev_longevity_daumcafe_full.csv | 278,662 | 277,056 / 1,606 | `다음카페` | `dc_` + sha1(쿼리를 뗀 URL)[:16] |

  합계 약 80만 행이다. 파일 안 `doc_id` 중복과 컬럼 수 불일치는 없다(2026-11-04 전수 점검). `doc_id` 규칙은 각 파일 앞 5,000행으로 확인했다.
- 지금 `dcxctl import-labels`는 파일 하나, 채널 `naver_cafe` 하나만 받는다. 다른 site는 `unknown_site`로 건너뛰고, `doc_id`·URL 정규화·날짜 해석이 네이버 카페 전용이다.
- DCX에는 `naver_kin` 채널(크롤러 있음)은 있지만 다음 카페·다음 브런치 채널은 없다.

## 컨트롤러가 정한 기본값 (계획 승인 때 함께 확인)

- 새 채널 이름은 `daum_cafe`(접두사 `dc`, 표시 "다음 카페")와 `daum_brunch`(접두사 `db`, 표시 "브런치")다. 파일의 `doc_id` 접두사와 맞춘다.
- 두 채널은 **가져오기 전용**이다. 크롤러를 만들지 않는다. 0단계 채널 선택지와 2단계 크롤링 설정에는 나오지 않는다. 가져온 프로젝트의 화면에서는 한글 이름으로 보인다.
- 지식인 `answers`(답변)는 저장하지 않는다. DCX `naver_kin` 크롤러도 "질문 제목과 본문(답변 제외)"만 수집하므로 같은 기준을 따른다. 작성자·댓글 닉네임은 이전처럼 저장하지 않고 작성자만 해시로 남긴다.
- 날짜는 `YYYY.MM.DD`(카페·지식인), ISO 8601(`2026-06-06T03:46:43+09:00`, 브런치), `YY.MM.DD HH:MM`(다음 카페, 20YY로 해석)을 모두 `YYYY-MM-DD`로 바꾼다. 비어 있거나 형식이 다르면 빈 값이다.

## 사용자가 보는 흐름

```
(서버) dcxctl import-labels ~/네이버\ 카페.zip ~/네이버\ 지식인.zip ~/다음\ 카페.zip ~/다음\ 브런치.zip
가져오기: 4개 파일 → imp-<묶음 해시>
검증  jev_longevity_full.csv 197,913행 · done 195,446 …   (파일마다 한 줄)
[1/5] 프로젝트 imp-… 만듦 (채널: 네이버 카페 · 지식iN · 다음 카페 · 브런치)
[2/5] 수집본 c1 등록 795,132건
[3/5] 전처리 … 진행률 …
[4/5] 라벨 …건 넣음
[5/5] 내보내기 완료
완료 → 웹에서 6단계(세그먼트)부터 진행
```

## 수용 기준

- AC1: `dcxctl import-labels <파일> [<파일> …] [--sid ID]`에 1~N개 파일을 주면 한 프로젝트가 만들어진다. 파일 하나만 주면 지금과 같은 프로젝트 id(`imp-` + 파일 sha256 앞 12자)와 결과가 나온다.
- AC2: 각 행의 `site`로 채널을 정한다: `네이버카페`→`naver_cafe`, `네이버지식인`→`naver_kin`, `다음카페`→`daum_cafe`, `다음블로그_브런치`→`daum_brunch`. 그 밖의 site는 지금처럼 `unknown_site`로 세고 건너뛴다.
- AC3: 채널마다 `doc_id`가 DCX 규칙(채널 접두사 + 정규화 URL의 sha1 앞 16자)과 같은지 확인한다. 다음 카페 정규화는 쿼리를 모두 뗀다. 파일 안이나 **파일 사이**에 `doc_id`가 겹치면 아무것도 쓰기 전에 멈추고 예시를 보여 준다.
- AC4: 프로젝트의 0단계 채널과 수집본 `manifest.channels`는 실제로 들어간 채널만 정해진 순서(네이버 카페, 지식iN, 다음 카페, 브런치)로 담는다. 각 문서의 `source`는 그 행의 채널이다.
- AC5: 3단계 전처리, 4단계 라벨, 5단계 내보내기, 6단계 세그먼트가 채널이 섞인 데이터로 오류 없이 끝난다. 6단계 채널 비율·근거 카드에 "다음 카페"·"브런치"·"지식iN"이 한글 이름으로 보인다.
- AC6: 일반 프로젝트의 0단계 채널 선택지와 2단계 크롤링 채널 표에는 `daum_cafe`·`daum_brunch`가 나오지 않는다. API로 이 채널만 골라 크롤링을 시작하면 지금처럼 "Sources are unavailable"(422)로 거절된다.
- AC7: 같은 파일 묶음으로 다시 실행하면 이어서 진행한다(파일 순서가 달라도 같은 묶음). 다른 묶음으로 같은 `--sid`를 쓰면 거절한다.
- AC8: 기존 네이버 카페 단일 파일 가져오기와 기존 채널 크롤링·전처리 동작은 바뀌지 않는다(회귀).

## 제외 범위

- 다음 카페·브런치 크롤러, 0단계에서 두 채널을 고르는 기능.
- 이미 만든 가져온 프로젝트에 채널을 나중에 덧붙이기.
- 확률 CSV(`*_probs.csv`) 사용, 웹 업로드 화면.
- 5단계 `model/export.write` 메모리 최적화(측정만 한다).
- 3단계 전처리 설정 화면의 채널 체크박스·상투어 탭에 두 채널을 넣는 것.

## 위험

- **규모:** 약 80만 건으로 네이버 카페 단독의 4배다. 3단계 전처리 시간·임베딩 비용(서버 `EMBED_BACKEND` 설정에 따름)과 5단계 내보내기 메모리가 커진다. 개발 PC에서 실제 4개 파일로 끝까지 돌려 시간·최대 메모리를 재고(가짜 임베딩), 서버 실행 전에 사용자에게 알린다.
- **표시 이름 목록이 선택지를 겸함:** 웹 `contextLabels.channels`가 0단계 선택지를, `channelNames`가 크롤링 설정 표를 만든다. 이름만 추가하면 두 채널이 선택지로 새어 나간다. 가져오기 전용 목록으로 걸러야 한다.
- **채널 이름 열거 지점이 여러 곳:** `Doc.source` Literal, `Channel` enum, `_PREFIXES`, 전처리 상투어 기본값, 백엔드·프론트 표시 이름. 하나라도 빠지면 검증 오류나 원시 키 표시가 난다.
- **날짜 형식 오해석:** `YY.MM.DD`를 `YYYY.MM.DD` 정규식이 일부만 잡지 않도록 형식별로 엄격하게 맞춘다.

## 설계가 필요한가

필요하다(`designNeeded: true`). 공유 모듈(채널 목록·URL 정규화·문서 스키마·0단계 선택지)에 가져오기 전용 채널이라는 새 개념이 들어가고, 여러 파일을 한 프로젝트로 묶는 식별 규칙(묶음 해시)을 정해야 한다. 화면은 새로 만들지 않고 기존 화면의 채널 이름 표시와 선택지 필터만 바뀌므로 목업은 만들지 않는다. 설계는 `02-design.md`에 적고 계획 번들에 함께 넣는다.
