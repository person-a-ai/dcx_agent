# label-import · 01 기획

- 작성: 2026-11-03 · 하네스 실행 `label-import` (full, base `d7d6827` = origin/main)

## 문제

- 사용자는 DCX 밖에서 이미 수집·라벨링을 끝낸 결과를 가지고 있다. 별도 크롤러(`ceragem-naver-portal-crawler`)가 만든 네이버 카페 CSV를 [`dcx-label`](https://github.com/person-a-ai/dcx-label)로 Jev 판정한 결과다.
- 이 결과로 DCX 5단계(세그먼트)부터 분석을 이어 가고 싶다. 그런데 지금 DCX에는 외부 결과를 넣는 길이 없다. 0단계 입력 → 1단계 키워드 → 2단계 크롤링 → 3단계 전처리 → 4단계 판정을 모두 화면에서 거쳐야 한다.
- 처음 받을 데이터는 `네이버 카페.zip`(약 1GB)이다.
  - `jev_longevity_full.csv`: 197,913행. 크롤러 원본 10개 컬럼과 dcx-label 결과 16개 컬럼으로 이뤄져 있다. `doc_id` 중복이 없다. `done` 195,446건, `skipped`(short_body) 2,467건이고, 모두 `네이버카페`이며 `q1`/`r1`이다.
  - `jev_longevity_full_probs.csv`: 같은 `doc_id`별 Jev 확률(`p_*`, `r_*`, `s_*`)과 `model=jev-1.14.0`이 들어 있다.

## 결정 (사용자, 2026-11-03 대화)

| # | 결정 |
|---|---|
| 1 | 웹 업로드 화면은 만들지 않는다. 사용자가 파일을 서버(Mac mini)에 직접 옮기고 **서버에서 명령 한 번**으로 가져온다. 진행 상황은 터미널 로그로 본다. |
| 2 | 0단계 입력 칸은 **전부 `.`**으로 채운다(제품명·한줄 정의 포함). 고르는 칸은 명령이 정한 기본값을 쓴다. 사용자는 아무것도 입력하지 않는다. |
| 3 | 1·2단계(키워드·크롤링)와 4단계(판정)는 건너뛴다. CSV 원본을 수집 결과로, CSV 판정을 최종 라벨로 그대로 넣는다. **Jev 판정만으로 최종 라벨을 만드는 것을 허용한다**(GPT 판정·교차 판정 없음). |
| 4 | 3단계 전처리(임베딩·토큰)는 5단계 이후에 필요하므로 건너뛸 수 없다. 명령이 기존 전처리 작업을 자동으로 실행한다. |
| 5 | 트랙 full. 화면이 없으므로 설계는 non-ui. |

## 사용자가 보는 흐름

```
(서버) dcxctl import-labels ~/네이버카페.zip
[1/4] 프로젝트 만듦        sid=…
[2/4] 수집본 등록          197,913건
[3/4] 전처리               … 진행률 …
[4/4] 라벨 넣음            done …건 · skipped …건 · 빠진 글 …건
완료 → 웹 프로젝트 목록에서 열고 5단계부터 진행
```

## 수용 기준

- AC1: 서버에서 `dcxctl import-labels <zip 또는 CSV>`를 한 번 실행하면 웹을 쓰지 않고 새 프로젝트가 만들어진다. 0단계 글 칸은 모두 `.`, 고르는 칸은 기본값(과제 유형 탐색, 채널 네이버 카페 등)으로 채워진다.
- AC2: 입력은 zip(안에 결과 CSV, 확률 CSV가 함께 있어도 됨)이나 결과 CSV 경로다. 필수 컬럼(원본 10개 + `doc_id, status`, 태그 8개, `evidence_level, reason_code, signal, questions_version, rule_version`)이 없으면, 판정 결과를 저장하기 전에 파일 이름과 빠진 컬럼을 알려 주고 멈춘다.
- AC3: CSV 원본은 2단계 수집본으로 등록되고, DCX는 그 수집을 '완료'로 본다. 웹의 1·2단계는 이 프로젝트에서 "가져온 수집본"으로 표시되고 크롤링을 요구하지 않는다.
- AC4: 3단계 전처리가 기존과 같은 코드와 같은 결과 형식으로 실행된다. 진행률은 터미널에 찍히고 웹 3단계 화면에서도 보인다.
- AC5: 전처리를 통과한 글 가운데 CSV에 `done` 판정이 있는 글은 그 판정이 최종 라벨이 된다(태그 8개, 등급, reason_code, signal). 출처는 가져온 라벨임을 알 수 있게 따로 표시한다. 4단계는 '완료'로 표시된다. GPT·Jev API는 호출하지 않는다.
- AC6: CSV의 `questions_version`/`rule_version`이 DCX의 현재 버전(`q1`/`r1`)과 다르면 가져오지 않고 멈춘다.
- AC7: 전처리 후 판정이 없는 글(`skipped`이거나 CSV에 없는 글)은 개수를 보고한다. 그 글은 최종 라벨에서 빠진다(5단계 입력 제외).
- AC8: 명령이 중간에 끊겨도 같은 명령을 다시 실행하면 같은 프로젝트에서 이어서 한다. 같은 파일로 프로젝트를 두 개 만들지 않는다.
- AC9: 끝나면 웹에서 그 프로젝트를 열어 5단계(세그먼트)를 평소처럼 실행할 수 있다.
- AC10: 승인된 검증 명령(백엔드 pytest, 프론트 lint·build·test)이 통과한다. 테스트는 작은 가짜 CSV로 하고, 모델·임베딩 호출은 기존 fake 백엔드를 쓴다.

## 제외

- 웹 업로드 화면.
- GPT로 다시 판정하기, Jev·GPT 교차 판정, 사람 검수 표본 뽑기(가져온 라벨에는 적용하지 않음).
- 확률 CSV(`*_probs.csv`)를 판정에 쓰는 것. 이번에는 결과 CSV만 쓴다.
- 지식인(`naver_kin`) 등 다른 채널. 이번 데이터는 네이버 카페뿐이다. 다른 `site`의 행은 건너뛰고 개수를 보고한다.
- 0단계 값을 나중에 채우는 별도 기능. 기존 화면이나 새 버전 만들기로 고친다.

## 위험

- **0단계 값이 `.`이면 6~8단계 결과가 주제 없이 나온다.** 사용자가 알고 선택했다. 명령 마지막 출력과 0단계 화면에 "가져온 프로젝트 · 0단계 미입력"이라고 표시한다.
- **수집 '완료' 판정이 수집 큐(`queue.sqlite`)에 묶여 있다.** 가짜 큐를 만들지 않고, 가져온 수집본임을 manifest에 표시해 완료로 인정하는 쪽을 설계에서 정한다. 다른 화면이 이 수집본에 크롤링 동작(재개·부분 종료)을 걸지 못하게 막아야 한다.
- **전처리가 글을 거른다**(광고어·제외 출처·중복·짧은 본문). 판정과 전처리 결과가 어긋나는 글은 AC7로 보고한다.
- **CSV에 없는 필드**: 댓글의 깊이·날짜·작성자, `src_meta`, `kw_axis` 등. DCX 문서 형식(`extra=forbid`)에 맞게 기본값을 채운다. 작성자 해시는 서버 salt로 닉네임을 해시한다(DCX 크롤러가 같은 사람에게 만든 해시와는 다르다).
- **규모**: 약 20만 건 전처리(임베딩)는 오래 걸린다. 진행률을 보이고, 끊기면 이어서 한다(AC8). 1GB 파일은 압축을 다 풀지 않고 스트리밍으로 읽는다.
- **4단계 완료 판정이 Jev·GPT 실행 기록에 묶여 있다**(`labelingDone`, `judge_done`). 가져온 라벨이 이 판정을 통과하면서 기존 프로젝트의 판정 흐름은 바뀌지 않도록 설계에서 정한다.

## 설계 필요 여부

필요하다. 화면은 없지만 가져온 수집본·라벨을 DCX의 완료 판정과 어떻게 맞출지, 명령 구조, 이어서 하기 방식, 기본값 표를 정해야 한다. `02-design.md`에 non-ui로 기록한다.
